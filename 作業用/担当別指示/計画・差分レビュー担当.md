# 計画・差分レビュー担当の作業指示

## 適用と前提

- ユーザーから「計画・差分レビュー担当」と明示された変更作業に適用する。資料の読込順はルート`AGENTS.md`に従い、本書を全文確認する。
- 計画、独立した差分確認、判定、計画終了、最終コミットを受け持つ。実装担当へ作業権を渡した後は、受領候補を自ら修正しない。

## 計画作成

保存する計画は次に従う。保存しない軽微変更は[該当節](#軽微変更を一貫して扱う例外)を使い、記録のためだけに計画を作らない。

1. ルート・HEAD・ブランチ、ステージ済み・未ステージ・未追跡差分を確認する。既存差分の所有者と扱いを明らかにし、対象パスに説明できない差分があれば実装へ渡さない。
2. 作業規模（単一／複数段階）、調査必要性、[変更リスク三分類](../技術仕様/自動検査・Git.md#変更リスクと完了検査)を別々に判定する。独立成果物が複数、三領域以上の横断、移行、一候補への限定が困難、同一フェーズで反復圧縮が見込まれる場合は複数段階の警告条件とし、ファイル件数だけでは決めない。
3. 複数段階では`大規模作業計画.md`へ全体条件・依存・段階境界、`実装計画.md`へ現在フェーズだけを記載する。相談の判断材料は`相談・事前調査.md`の使い方に従って記録・更新・終了する。大規模計画と相談記録は互いの必須条件ではない。
4. 保存を明示依頼された場合だけ`実装計画.md`を「計画あり」にし、同書の使い方・記入欄に従って目的・範囲・制約を具体化する。主要な完了条件を入口・責務境界・観測方法・期待結果へ対応させ、「実装済み」「問題がない」だけで済ませない。
5. 抽出・移設・削除・名称変更の参照探索と、随伴範囲の定義は[計画範囲と条件付き随伴ファイル](../技術仕様/自動検査・Git.md#計画範囲と条件付き随伴ファイル)に従う。判明した連動ファイルは既知パスへ列挙し、未調査のまま随伴範囲へ委ねない。仕様・期待結果を変える変更を随伴更新として承認しない。
6. 既知パスを列挙したら同節の予定パス判定で適用規則・選択範囲・完全フォールバックを確認し、検査計画へ記録する。未知パス・想定外のフォールバック・影響拡大があれば承認前に範囲または分割を見直す。これは依存探索や検査の実行を代用しない。
7. `進行中の作業.md`を「進行中」とし、基準HEAD・現在段階・次担当を記録する。実装を現在のユーザー指示で求められている場合だけ「実装待ち」「実装担当」として渡す。一貫担当では次担当を自分のままにする。「計画あり」は実装許可ではない。

目的・範囲・実装手順・完了条件を変える場合は必要なユーザー判断を得て計画を更新する。進捗は進行記録へ置き、計画を複製しない。

### 高リスク・横断計画の具体化

- 高リスク・横断・未知変更では、[横断契約の計画と観測](../技術仕様/自動検査・Git.md#横断契約の計画と観測)に従い、重要な状態の所有者・入口・利用先・観測方法を追跡できる記述と必要な受入シナリオを計画へ置く。形式は選べるが、必要な対応関係を省略しない。
- 保存・API・共通状態の連動先、取消・失敗・競合・再読込、時刻・非同期・外部副作用は同節の該当観点で具体化する。十分な既存記述に追加帳票を重ねず、段階境界の変更はユーザーへ相談する。

## 軽微変更を一貫して扱う例外

- ユーザーが計画・差分レビュー担当へ実装も明示し、実装担当へ作業権を渡す前である場合だけ選択できる。
- 仕様、API、セーブ、外部通信、課金、セキュリティへ影響しない局所的な変更に限定する。計画を保存する場合は担当欄へ一貫担当を明記する。保存しない場合は、ユーザーの明示依頼、対象範囲、終了条件を`進行中の作業.md`の「目的」へ短く記録する。
- 開始前にGit状態と既存差分を確認し、進行記録の基準HEAD・現在段階・次担当を設定する。編集、候補固定、検査、差分確認、最終化まで同じ担当が受け持つ。候補固定は[「最終候補と検査結果の同一性」](../技術仕様/自動検査・Git.md#最終候補と検査結果の同一性)、確認と終了は本書の該当節に従う。計画がない場合は記録した依頼範囲・終了条件を照合基準とし、自己点検を別担当による独立レビューとは扱わない。
- 実装担当が固定したレビュー候補をレビュー担当が修正する根拠にはしない。境界を明確にできない場合は通常の役割分担を使う。

## 差分レビュー

1. 進行記録が「レビュー待ち」または「再レビュー待ち」で、次担当が自分であることを確認する。
2. 判定前に[候補定型検査](../技術仕様/自動検査・Git.md#レビュー候補の定型検査)を再実行し、基準HEAD・tree IDと[検査対象の同一性](../技術仕様/自動検査・Git.md#最終候補と検査結果の同一性)を確認する。
3. `git diff --cached`を正本とし、候補・候補外差分・関連コード・設定・資料を実装報告とは独立に確認する。計画の目的・範囲・完了条件・採用済み判断・停止条件と照合する。
4. 主要な完了条件を実際のassert・観測箇所に対応させる。高リスク・横断・契約変更は[観測節](../技術仕様/自動検査・Git.md#横断契約の計画と観測)から、状態・連動先・保証する層を検索結果と差分で確認する。追加・変更した試験は[試験の維持基準](../技術仕様/自動検査・Git.md#自動試験を追加維持する基準)も確認し、別の層を保証済みとせず、不要な重複試験を要求しない。
5. 候補全体に[変更リスクと完了検査](../技術仕様/自動検査・Git.md#変更リスクと完了検査)が適用され、進行記録の有効な検査・未解決事項・実機確認が一致することを確認する。未完了の実行や予定表示だけを合格にしない。古い候補・解消済み失敗・秘密情報・不要なログを残さない。
6. Node試験の並列入口・資源隔離の変更や不安定性調査では、[基本確認](../技術仕様/自動検査・Git.md#変更後の基本確認)と[試験構成](../技術仕様/自動検査・Git.md#powershell試験ソース契約の構成)の追加結果・資源所有も確認する。承認前に現候補へ有効な合格結果を揃え、同一候補の有効な完了検査は繰り返さない。

判定は次のいずれかとする。

- **承認**：計画の完了条件を満たし、必要な検査と文書更新が済んでいる。
- **修正要求**：計画内の安全な修正で解消できる不備がある。
- **計画再確認**：仕様判断、対象拡大、完了条件変更、データ削除、外部通信、課金など、ユーザー判断または計画変更が必要である。

## 修正要求と再レビュー

- 役割分担では、修正要求を`作業用/進行中の作業.md`の「未解決事項」へ番号付きで記録し、「現在状態」を現在段階「修正待ち」、次担当「実装担当」へ置き換える。候補ファイルをレビュー担当が直接修正せず、ステージ済みレビュー候補を保持したまま実装担当へ渡す。一貫担当では自ら修正し、候補変更に応じた検査と差分確認を行う。
- 指摘は、再現条件、違反する不変条件、必要な修正結果、解消確認に使う試験または実機手順が判断できる具体性で記載する。横断する主要な状態を「等」で省略して追加の解釈へ委ねない。既存の計画・契約に対する不足か、差分から新たに判明したリスクかを区別し、新しい仕様判断や完了条件変更は修正要求へ混ぜず計画再確認とする。同じ原因の手戻りが続く場合は、個別修正を続けるか入力分類・状態遷移・試験観点を見直すかを判断する。
- 非同期・時刻境界の指摘は[観測節](../技術仕様/自動検査・Git.md#横断契約の計画と観測)に従って再現位置・観測値・対照ケースまで指定し、実装担当へ曖昧な試験設計を委ねない。
- 再レビューでは番号ごとの対応と直前候補からの差分を確認する。[「レビュー指摘後の増分検査」](../技術仕様/自動検査・Git.md#レビュー指摘後の増分検査)の適用条件と対象外条件を独立して照合し、適用できる場合は直前の完了検査と今回の増分検査を合わせて承認根拠にする。適用できない場合は候補全体の再分類と完了検査を求める。
- 解消済みの指摘と対応本文は「未解決事項」から削除し、現在候補の承認に必要な結果だけを「現候補と有効な検査」へ短く残す。未解決番号は付け替えない。
- 仕様、範囲、完了条件の変更が必要な場合は「計画再確認」とし、現在段階を「計画再確認待ち」、次担当を「ユーザー」として作業を止める。

## 承認後の最終化

- 実機確認または外部条件だけが残る場合は、「現在状態」のレビュー判定を「承認」、現在段階を「レビュー待ち」、次担当を「ユーザー」とし、「実機・外部確認」へ内容、確認担当、確認可能になる条件を記録する。未確認の完了条件が残る間はコミットしない。
- レビュー承認後の実機確認で候補ファイルが変わっていなければ、コミット前に同じ自動検査を繰り返さない。候補が変わった場合は承認を取り消し、変更リスクまたは増分検査条件に従って再レビューする。
- すべての完了条件を満たしたら、通常モードの候補定型検査と承認済みtree IDを最後に確認してから、`作業用/実装計画.md`と`作業用/進行中の作業.md`を状態「なし」の空テンプレートへ戻す。完了履歴は一時資料へ残さず、Gitコミットを正本とする。
- 大規模作業の一フェーズを終える場合は、大規模計画を閉じず、完了コミット、次フェーズ、変更した前提を更新する。全フェーズが完了した場合だけ、恒久情報を正本へ蒸留して`大規模作業計画.md`と`相談・事前調査.md`も空テンプレートへ戻す。
- 調整文書の閉鎖後は[「調整文書を閉じた後の最終化」](../技術仕様/自動検査・Git.md#調整文書を閉じた後の最終化)に従い、承認済みtree IDで最終化検査を行う。調整文書自体を改訂した場合は、閉じたテンプレートを含む最終差分もレビュー・承認する。検査に合格するまでコミットしない。
- 最終化モード、最終ステージ対象、部分ステージ、差分空白、対象外差分、未追跡ファイルを確認し、結果が分かる日本語の件名で1作業1件のローカルコミットを作成する。技術手順は`作業用/技術仕様/自動検査・Git.md`を正本とする。

## 中止時の終了処理

- この手順は、ユーザーが事前調査、大規模作業全体、または現在の変更作業の中止・撤回を明示した場合だけ使用する。相談記録だけで実装差分がない場合の終了は`相談・事前調査.md`の使い方に従う。待機、保留、追加確認、計画再確認、単一フェーズの見直しを中止と推測しない。
- 新しい変更を止め、基準HEAD、完了済みコミット、ステージ済み・未ステージ差分、未追跡ファイル、未完了条件を確認する。中止指示だけを根拠に、実装差分の破棄、完了済みコミットの取消し、ファイルの削除・復元を行わない。
- 未完了の実装差分や保存データなどについて、保持、別作業への引継ぎ、破棄の判断が必要な場合は、`進行中の作業.md`の「現在状態」を現在段階「中止処理待ち」、次担当「ユーザー」とし、判断対象を「未解決事項」へ記録してユーザーへ確認する。ユーザーの判断前に調整文書を閉じない。
- 中止後も有効な承認済み方針、確認済み事実、内部契約だけを該当する恒久資料へ蒸留し、未完了の案や未確認の推測を現行仕様として残さない。中止対象の差分とデータの扱いが確定した後、対象となる`実装計画.md`と`進行中の作業.md`を空テンプレートへ戻し、大規模作業全体または事前調査を閉じる場合は`大規模作業計画.md`と`相談・事前調査.md`も空テンプレートへ戻す。中止を完了として記録しない。

## 停止条件

- 基準コミット不一致、説明できない既存差分、候補外の変更、検査不能、秘密情報混入、対象範囲外の仕様判断を発見した場合は判定または最終化を進めない。
- 実装担当から受け取ったレビュー待ち・再レビュー待ちの候補を変更する必要がある場合は、自分で修正せず修正要求として実装担当へ戻す。
