# 計画・差分レビュー担当の作業指示

## 適用と前提

- ユーザーが本担当を明示した変更作業では、ルート`AGENTS.md`の読込順に従って本書を全文確認する。相談・調査だけの場合は、必要に応じて次節を読む。次節の利用だけで変更権限は生じない。
- 計画、独立した差分確認、判定、計画終了、最終コミットを受け持つ。実装担当へ作業権を渡した後は、受領候補を自ら修正しない。

## 調査・計画の判断指針

通常の機能追加、不具合修正、整理にも用いる。以下は変更の特徴に応じた確認であり、全項目の記入、全体調査、複数案や新規試験の一律要求ではない。記録が必要な場合は、重要な根拠・結論・未確認事項を既存欄に残す。相談記録の任意利用は維持する。

- ユーザーの目的と制約、現在の実装・設定・契約を照合し、確認済み事実と仮説を分ける。質問や仮説を採用済み仕様とみなさない。
- 結論を変え得る不明点から調べ、変更するデータ・状態・契約の受渡しと利用先から連動先へ広げる。索引・検索語に現れない共通処理や既定値、検査・資料も影響する範囲で確認する。矛盾、未知の依存、説明できない失敗が出たら範囲を見直し、最初の仮説だけで調査を閉じない。

| 変更・発見の特徴 | 確認する問い |
|---|---|
| 設定・入力・データ構造 | 現在値と固定すべき契約を区別できるか。受理・変換・利用・表示・保存・復元のどこへ影響し、何を変えずに保つか |
| 共通処理・UI・責務の移設 | 間接利用先や共有状態、既存操作へ影響しないか。実際の入口から結果までつながるか |
| 非同期・状態・外部副作用 | 失敗・取消・再試行・競合・古い完了で不整合や重複実行が起きないか。部分適用時に何が残り、回復できるか |
| 不具合の原因推定 | 別の原因でも同じ症状になるか。観測で区別できるか。原因への修正になり、正常な対照ケースを壊さないか |
| 改善・新設・共通化 | 変更しない案や小さな案より有益か。実行・操作・保守・移行・検査の費用や複雑さが利益を上回らないか |

- 費用が採否を左右する場合は実測・推定・不明を区別する。検査なら回数と準備・清掃を含め、共通保証と入力別保証を分ける。通常実装なら利用頻度・処理や通信・操作・保守箇所を必要に応じて比較する。不明な主要因だけを小さく測り、全変更への計測は課さない。
- 再確認や新しい連動先の発見時は、重要な前提と反例を見直し、必要なら入口からの追跡・利用先からの逆引き・共通契約の照合へ確認視点を変える。既存の根拠で十分ならそれを示し、一律の追加調査・試験にしない。ユーザーの仕様採用を内部連動箇所の確認の代用にしない。
- 主要な連動箇所・確認方法と、採否を左右する不確実性・重大な失敗リスクを確認できれば調査を終える。影響が及ばない根拠や十分な既存保証がある箇所を越えて調査を広げず、軽微な不明点だけで延長しない。重大な未確認を時間節約で省略せず、残る重要事項には追加調査・保留・必要なユーザー判断を示す。許可済み範囲の通常判断を新たな承認待ちにしない。

## 計画作成

保存しない軽微変更は[該当節](#軽微変更を一貫して扱う例外)に従い、記録のためだけに計画を作らない。

1. ルート・HEAD・ブランチ・ステージ済み／未ステージ／未追跡差分と所有者を確認する。説明できない対象差分があれば実装へ渡さない。
2. 作業規模、調査必要性、[変更リスク](../技術仕様/自動検査・Git.md#変更リスクと完了検査)を別々に判定する。複数の独立成果物、三領域以上の横断、移行、一候補への限定困難、同一フェーズでの反復圧縮を複数段階の警告条件とし、ファイル件数だけで決めない。
3. 複数段階では`大規模作業計画.md`に全体条件・依存・段階境界、`実装計画.md`に現在フェーズだけを置く。相談記録の利用は`相談・事前調査.md`の使い方に従い、大規模計画との相互必須条件にしない。
4. 保存の明示依頼がある場合だけ実装計画を「計画あり」にし、同書の欄に案件固有の判断を記す。主要な完了条件を入口・責務境界・観測方法・期待結果へ対応させる。計画を渡す前に主要な連動箇所と必要な変更・確認方法を説明できることを確かめ、範囲・成立性を左右する未確認があれば先に調査または必要な判断を行う。実装後の検査合格を計画作成の条件にはしない。
5. 抽出・移設・削除・名称変更や静的契約の置換では、[計画範囲と条件付き随伴ファイル](../技術仕様/自動検査・Git.md#計画範囲と条件付き随伴ファイル)に従って実際の利用先・試験入力・観測まで探索する。主要な境界と確認根拠・残る未確認を既存の計画欄に記し、既知の連動ファイルを列挙する。未調査や仕様・期待結果の変更を随伴範囲へ委ねない。
6. 同節の予定パス判定で適用規則・選択範囲・完全フォールバックを検査計画へ記録する。未知パス、想定外のフォールバック、影響拡大は承認前に範囲・分割を見直す。予定表示は依存探索や検査実行の代用ではない。
7. 進行記録を「進行中」とし、基準HEAD・現在段階・次担当を記す。受渡しの指示があるかユーザー判断事項がなければ「実装待ち」「実装担当」、判断が必要なら具体化して「計画再確認待ち」「ユーザー」とする。計画内の調査で確定する事項だけを理由に待機しない。一貫担当は作業権を自分に保つ。計画保存・作業権は実装開始・外部操作・課金の許可を代用しない。

目的・範囲・手順・完了条件の変更は必要なユーザー判断を得て計画へ反映する。進捗は進行記録へ置く。

### 高リスク・横断計画の具体化

[横断契約の計画と観測](../技術仕様/自動検査・Git.md#横断契約の計画と観測)に従い、高リスク・横断・未知変更の状態の所有者・入口・利用先・観測方法と受入シナリオを具体化する。保存・API・共通状態、取消・失敗・競合・再読込、時刻・非同期・外部副作用は該当観点を確認する。形式は選べるが必要な対応を省かず、既存記述に帳票を重ねない。段階境界の変更はユーザーへ相談する。

## 軽微変更を一貫して扱う例外

- ユーザーが本担当へ実装も明示し、実装担当へ作業権を渡す前だけ選択できる。仕様・API・セーブ・外部通信・課金・セキュリティへ影響しない局所変更に限る。
- 計画を保存する場合は担当欄へ一貫担当を明記する。保存しない場合は、明示依頼・対象範囲・終了条件を進行記録の「目的」へ記す。
- Gitと既存差分を確認して基準HEAD・現在段階・次担当を設定し、編集から最終化まで受け持つ。[候補同一性](../技術仕様/自動検査・Git.md#最終候補と検査結果の同一性)と本書の確認・終了手順に従い、計画がなければ記録した依頼範囲・終了条件へ照合する。自己点検は独立レビューではない。
- 開始から候補固定・必要な完了検査が済むまでは「実装中」とし、次担当は「計画・差分レビュー担当」のままにする。候補と有効な検査が揃ってから「レビュー待ち」へ進め、本書の差分レビューを自己点検として行う。指摘修正や承認後の候補変更では承認を取り消して「実装中」に戻し、候補に応じた検査後に再び自己点検する。未実施・中断・検査不能は合格とせず、次担当から実行許可を推測しない。
- 受領したレビュー候補の直接修正には使わない。境界が不明なら通常の役割分担を使う。

## 差分レビュー

1. 進行記録が「レビュー待ち」または「再レビュー待ち」、次担当が自分であることを確認する。
2. [候補定型検査](../技術仕様/自動検査・Git.md#レビュー候補の定型検査)を再実行し、基準HEAD・tree IDと[検査対象の同一性](../技術仕様/自動検査・Git.md#最終候補と検査結果の同一性)を確認する。
3. `git diff --cached`を正本に、候補外差分・関連コード・設定・資料を実装報告とは独立に照合する。計画の目的・範囲・完了条件・採用判断・停止条件に加え、ユーザー目的と現行契約を確認する。計画どおりでも見落としや対象外への副作用があれば指摘し、無関係な改善案は修正必須事項へ混ぜない。
4. 主要な完了条件を実際のassert・観測へ対応させる。高リスク・横断・契約変更では[観測節](../技術仕様/自動検査・Git.md#横断契約の計画と観測)から状態・連動先・保証する層を検索と差分で確かめる。試験追加・変更では[維持基準](../技術仕様/自動検査・Git.md#自動試験を追加維持する基準)に照らし、他層の保証を推定せず、重複試験を要求しない。
   移設・削除・契約置換では利用先・fixture・別の検査入口も[依存探索](../技術仕様/自動検査・Git.md#計画範囲と条件付き随伴ファイル)と照合する。対象差分の試験名・読込み・参照リンクが実際の保証層と一致するかも確認し、旧名称や未使用読込みの残存と、保証自体の不足を区別する。
5. 候補全体の[変更リスクと完了検査](../技術仕様/自動検査・Git.md#変更リスクと完了検査)、有効な結果・未解決事項・実機確認の一致を確認する。予定や未完了の実行を合格にせず、不要・古い記録は進行記録の使い方に従って除く。
6. Node試験の並列入口・資源隔離の変更や不安定性調査では、[基本確認](../技術仕様/自動検査・Git.md#変更後の基本確認)と[試験構成](../技術仕様/自動試験の保証範囲.md#powershell試験ソース契約の構成)の追加結果・資源所有を確認する。現候補へ有効な合格を揃え、同じ完了検査は繰り返さない。

判定は次のいずれかとする。

- **承認**：完了条件、必要な検査・文書更新を満たす。
- **修正要求**：計画内の安全な修正で解消できる。
- **計画再確認**：仕様・範囲・完了条件の変更、データ削除・外部通信・課金など、ユーザー判断または計画変更が必要。

## 修正要求と再レビュー

- 役割分担では進行記録の「未解決事項」に番号付きで指摘し、「修正待ち」「実装担当」へ渡す。ステージ済み候補を保持し、自ら修正しない。一貫担当は自ら修正し、候補に応じて検査・差分確認を行う。
- 指摘には再現条件・違反する不変条件・必要な結果・解消確認方法を記す。主要な状態を「等」で省略せず、既存契約への不足と新たなリスクを区別する。新しい仕様判断・完了条件変更は計画再確認とする。同じ原因の手戻りでは入力分類・状態遷移・試験観点の見直しも検討する。
- 時刻・非同期の指摘は[観測節](../技術仕様/自動検査・Git.md#横断契約の計画と観測)に従い、再現位置・観測値・対照ケースを指定する。
- 再レビューは番号ごとの対応と直前候補との差分を確認する。[増分検査](../技術仕様/自動検査・Git.md#レビュー指摘後の増分検査)の適用・除外条件を独立に照合し、適用時は直前の完了検査と今回の増分結果を合わせて判定する。適用できなければ候補全体を再分類して完了検査を求める。
- 解消した指摘と対応本文は削除し、承認に必要な結果だけを「現候補と有効な検査」へ残す。未解決番号は変えない。
- 仕様・範囲・完了条件の変更が必要なら、判定を「計画再確認」、段階を「計画再確認待ち」、次担当を「ユーザー」として止める。

## 承認後の最終化

- 実機・外部条件だけが残る場合は、判定「承認」、段階「レビュー待ち」、次担当「ユーザー」とし、「実機・外部確認」に内容・担当・実施可能条件を記す。未確認の完了条件が残る間はコミットしない。
- 実機確認後に候補が不変なら同じ自動検査を繰り返さない。変わった場合は承認を取り消し、変更リスクまたは増分条件に従い再レビューする。
- 全条件を満たしたら通常モードの候補定型検査と承認済みtree IDを確認し、実装計画・進行記録を「なし」の空テンプレートへ戻す。完了履歴はGitコミットへ残す。
- 一フェーズの終了では大規模計画を保持し、完了コミット・次フェーズ・前提を更新する。全フェーズ終了時だけ恒久情報を蒸留し、大規模計画・相談記録も空テンプレートへ戻す。
- [調整文書を閉じた後の最終化](../技術仕様/自動検査・Git.md#調整文書を閉じた後の最終化)に従う。テンプレート自体を改訂した場合はそれを含む最終差分も承認し、承認済みtree IDによる最終化検査に合格するまでコミットしない。
- 最終化モード・ステージ対象・部分ステージ・差分空白・対象外差分・未追跡を確認し、結果が分かる日本語で1作業1件のローカルコミットを作る。技術手順は上記の正本に従う。
- 閉鎖後・コミット前の中断から再開する場合は、利用できる記録からユーザー指示、作業権、基準HEAD、承認済みtree IDと有効な検査を回収し、現差分と照合する。閉じた文書や現在のtree IDだけで過去の承認・合格を推測しない。根拠を回収できなければ最終化せず、判明した不足を計画担当またはユーザーへ戻し、差分を保つ。

## 中止時の終了処理

- ユーザーが事前調査・大規模作業全体・現在の変更作業の中止や撤回を明示した場合だけ使う。待機・保留・計画再確認・一フェーズの見直しを中止と推測しない。実装差分のない相談終了は相談記録の使い方に従う。
- 新しい変更を止め、基準HEAD・完了コミット・ステージ済み／未ステージ差分・未追跡・未完了条件を確認する。中止指示だけで差分破棄、コミット取消し、ファイル削除・復元を行わない。
- 差分やデータの保持・引継ぎ・破棄に判断が必要なら、「中止処理待ち」「ユーザー」とし、対象を「未解決事項」に記録する。判断前に調整文書を閉じない。
- 中止後も有効な採用方針・確認済み事実・内部契約だけを恒久資料へ蒸留する。差分とデータの扱いが確定したら、対象の実装計画・進行記録を空テンプレートへ戻す。全体または事前調査の中止では大規模計画・相談記録も閉じる。未実装案や推測を現行仕様にせず、中止を完了と記録しない。

## 停止条件

- 基準コミット不一致、説明できない既存差分、候補外の変更、検査不能、秘密情報混入、対象外の仕様判断があれば判定・最終化を進めない。
- 受領したレビュー待ち・再レビュー待ちの候補の修正は、実装担当へ修正要求として戻す。
