# 臨時：運用整備の相談方針

状態：文書改訂完了（相談資料として保持）

最終更新：2026年10月2日

## この文書の位置付け

- 今回の運用整備について、コンテキスト圧縮・チャット再開後も前提と判断を保持し、相談を続けるための臨時文書である。ユーザーの明示依頼により作成した。
- 担当は、この相談でユーザーが指定した「運用点検・整備担当」。通常の計画・差分レビュー担当または実装担当への就任、恒久的な第三担当の新設を意味しない。
- ユーザーは相談・調査・臨時計画の作成後、このチャットの臨時担当のまま修正と自己点検を行うことを明示し、作業実施を指示した。通常の二担当へは割り当てず、今回の担当規則を恒久文書へ追加しない。臨時三文書へ今回限りの進め方と結果を保存する。
- 本書は現行規則や実装計画を置き換えない。以下の整理案を保存したことだけで、個々の記述の削除・移動・変更が承認されたとは扱わない。
- 今回の相談方針は本書に集約し、[追加調査メモ](臨時_運用整備_追加調査メモ.md)は調査根拠と限界、[文書改訂計画](臨時_運用整備_文書改訂計画.md)は変更範囲・改訂内容・受入条件・実施方法を所有する。方針全文を複製せず、通常の実装計画・進行記録を記録目的だけで有効化しない。
- 更新する場合は現在有効な内容へ置き換え、毎応答の追記や作業日誌にしない。相談の終了・中止や改訂完了時に、必要な情報の移管と本書の扱いを決める。無断で恒久資料化・削除しない。

## ユーザーが明示した前提と目的

- タスクの並列化は志向しない。
- 「相談 → 調査 → 計画立案 → 実装担当による実装 → 差分レビュー → 問題がなければ実装終了、指摘があれば実装担当へ戻して修正・再レビュー」という基本サイクルを維持する。
- 各文書に記載する内容を整理し、責務を明確にする。特にルート`AGENTS.md`と各担当向け文書に整理の余地があるかを検討する。
- `AGENTS.md`と各担当向け文書を軽量にし、常時読み込むコンテキストトークンの負荷を下げつつ、必要な文書を必要な時に読み込む。
- プロジェクト遂行においてAIの判断・行動に不要な情報は削除したい。ユーザーが節目でZIP保存しているという情報は、その検討例である。
- 運用を維持しながら、判断や思考の柔軟性まで形式で拘束しない。一方、ユーザーの軽量化の好みに合わせて必要な記載を形式的に移設・削除することも避け、必要な情報は残す。
- 目的は運用と文書の改善である。根拠のある実務上の推奨がユーザーの好みと異なる場合も、その理由・影響を示して提案できる。これは明示された権限・保護条件や変更範囲を越える許可ではない。

## 判断の基礎となるユーザーの思想

- AIは事実・根拠・論理と今回の目的に照らして独立に判断し、許可された範囲内で必要な調査・検証・作業方法を選ぶ。
- 検討観点、手順、文書は、判断の質と作業の確実性を支える手段である。項目を埋めることや手順を消化すること自体を成果にしない。
- 重要な問題は十分に掘り下げる。一方、結論や成果に寄与しない網羅・形式・作業を増やさない。
- 明示された権限、保護条件、採用済み方針を尊重する。改善の必要性は目的と影響から判断し、改善可能という理由だけで範囲を広げない。
- 判断・検証の限界を隠さず、必要な根拠とともに伝える。

## 今回の整理の方向

基本サイクルと二担当制を維持したまま、常時読込負荷を抑え、必要な場面で必要な情報へ到達できる構成を目指す。判断基準・権限・技術契約による責務分離はその手段であり、それ自体を目的にしない。各記述について「これがAIの判断・行動・検証をどう変えるか」を確認する。文字数は負荷の補助情報であり、トークン数や品質改善そのものではない。削減文字数、統合ファイル数、帳票の充足だけで成果を評価しない。

並列化、二担当制の廃止、軽微変更の別経路の新設は、今回の目的に対する提案の中心から外す。

| 大規模計画・相談記録 | 必要な場合の段階境界、判断材料 | 毎作業での形式的な記入、他文書の複製 |

### AGENTS.mdと担当別文書の整理観点

- `AGENTS.md`には、全作業で必要な境界と、コードからは分からない誤操作防止情報を優先して残す。
- `AGENTS.md`自体も軽量化の明確な対象とする。正本関係の重複、進行記録の更新詳細、随伴更新の詳細、参照指示の反復、ZIP保存習慣を整理する。必要な境界を残した軽量化を推奨し、削減率を先に決めて必要情報を削らない。
- ユーザー調整値、正式な編集元、実API・課金の許可、退避物・セーブ・画像の保護、担当・作業権、相談と実装開始の区別は重要な判断材料である。
- ユーザーの思想は共通原則として簡潔に置く案とし、各担当文書へ同じ説明を複製しない。
- 担当別文書では、守る条件と選べる方法を区別する。実装担当が目的・範囲・完了条件を独断で変えないこと、レビュー担当が受領候補を直接修正しないこと、未確認の完了条件を完了扱いしないことは維持する。
- 調査順序、試験の組合せ、表などの表現形式は、その目的を達成できるかで判断する。「状態の所有者 × 入口・利用先 × 観測方法」の成果は表の作成ではなく、重要な状態と責務境界の見落としを防ぎ、根拠をレビュー可能にすることである。ただし、候補の同一性確認や作業権の受渡しなど、順序・手順自体が保証を支えるものは残す。現行の必須手順を、相談中の案だけで任意扱いに変えない。
- 特定の時刻境界などの細かな検証方法は、一般的な担当手順から技術仕様の該当節へ集約することを検討する。必要な具体性を削って「適切に検証する」だけにしない。
- 基準HEAD・tree IDと検査結果の対応、リスクに応じた検査、増分検査、実機確認の保証範囲は、短文化だけを理由に弱めない。

### 記述を選別する基準

| 分類 | 判断基準 |
| --- | --- |
| 残す | 権限・保護・採用済み方針・重要な判断を直接左右する |
| 移す | 必要時の参照に適し、読む条件と参照先を明確にしても判断・保証を損なわない |
| 統合する | 同じ条件を複数箇所で定義している |
| 削除する | 判断・行動に影響せず、再開や誤修正防止にも不要 |

- 重複ゼロを目的にしない。受渡し地点の短い注意や参照は必要に応じて残せる。同じ詳細条件・手順を複数文書が独立して定義する状態を避ける。
- 配置は、必要になる頻度、読み落とした影響、参照の確実性、判断への寄与を併せて選ぶ。必要だと気づくための記述は入口に残し、詳細を読む条件を示す。
- 移設した本文だけでなく、参照指示、参照先で実際に読む量、探索の手間も含めて負荷を判断する。短い重要事項を移して毎回別文書を開くなら、改善にならない場合がある。
- 技術仕様が長いこと自体を欠陥にしない。毎回読む量と該当節への到達性を確認し、分割による参照・更新負担も考慮する。
- 必要性を点検した結果、削減余地が小さい箇所はそのまま残せる。文字数目標を達成するために判断材料を削らない。
- ユーザーの習慣、AIの担当決定に使わないモデル名、過去経緯、解消済み問題の説明も、現在の判断に必要かで選別する。未確認のまま一括削除しない。
